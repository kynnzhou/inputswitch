# InputSwitch

一台显示器接两台主机，**点一下或按一个热键**就把屏幕切过去，不用伸手去按显示器上的按钮。

Windows / macOS 双端，原生二进制，目标机器不需要装 Python、Node 或任何运行时。

---

## 怎么用（三步，不用开终端）

**1. 打开程序**

- macOS：把 `InputSwitch.app` 拖进「应用程序」，双击
- Windows：双击 `InputSwitch.exe`

菜单栏（macOS）/ 系统托盘（Windows）出现一个 ⇄ 图标。

**2. 设一下热键目标**

点图标 → `打开控制面板…` → 「输入源」里找到**另一台电脑**接着的那个口 → `设为目标`。

> 例：显示器 DP 口接 Windows、USB-C 口接 Mac。
> 在 Mac 上就选 `DP-1`；在 Windows 上就选 `USB-C`。
> 含义是"按热键时，把屏幕推给对面那台"。

**3. 按热键**

默认 `Ctrl+Alt+S`（Mac 上是 `Control+Option+S`）。屏幕立刻切到对面。

菜单里也有 `切换输入源`，点哪个口就切哪个口，不用热键也能用。

**开机自启**：面板「设置」里点一下，macOS 写 LaunchAgent，Windows 写注册表 Run 键。

## 为什么是"推给对面"而不是"拉回自己"

这是 DDC/CI 的物理约束，不是设计选择：

> 显示器一旦切到另一个输入口，本机的 DDC 通道就断了。

所以**只有当前正在显示的那台机器能发指令**。你在 Windows 上想把屏幕拿回来是做不到的 ——
必须由 Mac 主动"推"过去。这也是为什么每台机器只需要配一个目标口。

补充一个实测到的细节：屏幕被切走后，那台机器的系统层面会认为**显示器被拔了**，
`EnumDisplayMonitors` 直接返回 0 台，连物理显示器句柄都拿不到。
所以面板的「输入源」在这种机器上是空的，并明确写"本机现在没有接通的显示器"——
这不是读取失败，是真的没有显示器可读。

这种情况下主按钮会变成 `请 <对端> 把画面切回本机（0x…）`：本机自己发不出 DDC，
但可以让握着画面的那台替你切（走局域网命令通道）。前提是本机成功读到过一次
自己接在哪个口 —— 接上屏幕启动一次就会记住并落盘。

## 第一次用如果切不动

按顺序排查，命中率从高到低：

1. **显示器 OSD 里把 DDC/CI 打开** —— 很多机器出厂是关的。INNOCN 在「其他设置」里。
2. **别经过扩展坞 / 转接头**，用线直连。DDC 在多数 hub 上会被吃掉。
3. 有的显示器只在 DP/HDMI 口转发 DDC，USB-C 口不转发。
4. 虚拟机、远程桌面里拿不到 DDC。

诊断命令（macOS 在 `.app/Contents/MacOS/inputswitch-cli`，Windows 是旁边的 `inputswitch-cli.exe`）：

```bash
inputswitch-cli probe       # 列出显示器、DDC 能力、当前输入源
inputswitch-cli selftest    # 同上，外加排查建议和退出码
inputswitch-cli status      # 当前状态 + 局域网里发现的对端
```

`✓ 可读可写` 最好；`△ 仅可写` 也能用（切换靠"显示器从拓扑里消失"来确认）；
`✗ 不可用` 就是那个口根本不转发 DDC。

## 如果标准值不对

MCCS 标准里 `0x60` 的取值是 15=DP、17=HDMI、27=USB-C，但**相当多显示器不遵守**，
尤其 USB-C 口基本是厂商私有码。

菜单里的口名后面标着实际会写下去的值（如 `DP-1 (0x0F)`）。如果点了没反应：

```bash
inputswitch-cli wizard --own usbc --other dp1
```

它会逐个遍历候选值，哪个让显示器从本机拓扑里消失，哪个就是那个口的真实值，并写进配置。

> ⚠️ 命中瞬间本机屏幕就黑了，恢复要靠对面那台按热键，或显示器 OSD 手动切回。

试出来后配置会按**显示器型号**存下来。因为取值由显示器固件决定，跟主机无关 ——
一台机器上试出来的结果，另一台拷过去直接能用。

## 配置文件

- macOS：`~/Library/Application Support/inputswitch/config.json`
- Windows：`%APPDATA%\inputswitch\config.json`

```json
{
  "hotkey": "ctrl+alt+s",
  "hotkey_target": "dp1",
  "labels": { "usbc": "Mac", "dp1": "Windows" },
  "monitors": {
    "P275MV PLUS": {
      "inputs": [
        { "name": "usbc", "value": 27, "verified": true },
        { "name": "dp1",  "value": 15, "verified": true }
      ]
    }
  }
}
```

面板「设置」底部的 `打开配置文件夹` 可以直接跳过去。日志在同目录的 `app.log`，出问题把它发我。

## 双机中继（可选）

两台机器都开着本程序时，会通过 UDP 广播（端口 47831）互相发现。

用途：如果 A 机的 DDC 不通但 B 机通，A 可以在本机切换失败时请 B 代劳 ——
因为 B 此刻正持有 DDC 通道。只要**任意一台**能用，双向都能切。

```bash
inputswitch-cli switch dp1 --relay
```

## 配对：别让别人的电脑动你的屏幕

点 `打开控制面板…` → 「配对」卡片里填。

两台填同一个码（6 位够用，越长越难猜）。保存后：

- 每条局域网消息都带 `HMAC-SHA256` 签名 + 时间戳 + nonce
- 验不过的直接丢，还会在面板上显示"被拒次数"
- 重放和篡改都过不去

没配对时不会拦人 —— 同一网段的任何设备都能给你的显示器发指令。
所以第一次用建议就把码填上。

```bash
inputswitch-cli pair --generate      # 生成一个随机码
inputswitch-cli pair 123456          # 直接设
inputswitch-cli pair                 # 看当前状态和密钥指纹
```

### 配对到底管什么（v0.6.57 起写清）

配对是**门禁，不是权限系统**。它管的是"哪些机器的网络消息能被听进去"，一共四处：

| 通道 | 管住的效果 |
|---|---|
| UDP `announce` | 签名不对的对端**进不了对端表**，等于不存在 |
| UDP `command` | 陌生人让你切屏、切口，直接丢 |
| TCP 文件 HELLO | 配对码不一致 → "配对码不一致，已拒绝" |
| 共用键鼠事件流 | ChaCha20-Poly1305 加密，未配对时明文 |

**完全不受影响的**：本机 DDC 切屏、控制面板（`127.0.0.1`，不对外）、托盘与热键、剪贴板本机内轮询、开机自启。也就是说，配对**不会**阻止谁在你的机器上点鼠标 —— 决定按键鼠能不能被注入的是另一件事：共用键鼠只认**链路表里的 IP**（`kvm/mod.rs` 收包处那条白名单），它和配对互相独立。

两个容易踩的点：

- **本机没填码、对端填了**：你的指令发得出去，但对面会当未签名包丢掉。v0.6.57 起这种情况会在托盘/面板里**明确报出来**，不再谎称"已请对端切屏"。
- **改完码要立刻生效**：共用键鼠的事件流密钥是启动时定的，文件接收的钥匙也是。v0.6.57 起保存配对码会自动重开共用键鼠、并换掉文件接收的钥匙，不用再手动关一次开一次。代价是当时正在转发的那一场会断 —— 换锁的时候门本来就该是关着的。

## 控制面板

菜单 → `打开控制面板…`，会弹出程序自己的窗口（不是浏览器标签页）。

一屏能看到所有状态：配对、每个输入口有没有主机、对端在哪台机器上、
热键、接收目录、传输进度。切换、改目标、扫描、传文件都在这里点。

窗口用的是系统自带的 WebView，不额外打包浏览器内核：

| 平台 | 内核 | 说明 |
|---|---|---|
| macOS | WKWebView | 系统自带，无额外依赖 |
| Windows | WebView2 | Win10 1803+ / Win11 自带；缺运行时会自动退回浏览器 |

页面本身跑在 `http://127.0.0.1:47833/`（只监听本机），窗口就是把这个地址装进去。
所以窗口实在开不出来时（比如 Windows 缺 WebView2 运行时），程序会**自动**改用
默认浏览器打开同一个地址 —— 功能一模一样，只是没了个窗口。命令行和脚本也能直接调这套接口。

### 托盘菜单只留四件事

托盘不再是第二个设置面板。能改配置的东西全在控制面板里，菜单只保留"不开窗口就能做完的事"：

| 菜单项 | 为什么留在托盘 |
|---|---|
| 状态两行 | 一眼看到当前口 + 这台显示器能不能被软件切 |
| `切换输入源 ▸` | 程序的核心动作，点两下就切完 |
| `<对端主机名> ▸` | 每台对端一个子菜单：切到它 / 把键鼠交给它 / 发文件给它 / 它摆在本机哪一侧 |
| `共用键鼠` + 模式切换 | 边用边切的开关，开窗口太慢 |
| `打开控制面板…` | 其余所有事情的入口 |
| `退出` | 总得有个地方退 |

对端子菜单是 v0.6.54 起的样子。以前是顶层平铺「切到 X（口）」，外加一个全局的
「对端在右侧 ✓/左侧/…」四选一 —— 一机四台时前者看不出哪行属于哪台，而后者
只对**一条链路**成立（v0.6.47 起每台各有自己的一条边），改一次会把四台的方向
一起改掉。现在方向是每台各一份，就在它自己的子菜单里。

配对、传文件、热键、热键目标、开机自启、剪贴板、检测支持性、扫描口、打开配置文件夹、
以及原来那个"在浏览器中打开面板"—— **全部只在面板里出现一次**，不再两边各放一份。

> **Windows 分发注意**：`x86_64-pc-windows-gnu` 构建出来的 exe，WebView2 的载入器
> 是**动态链接**的（`webview2-com-sys` 只在 `target_env = "msvc"` 时才用静态库），
> 所以 `WebView2Loader.dll` 必须和 `InputSwitch.exe` 同目录，否则双击直接弹
> 「由于找不到 WebView2Loader.dll，无法继续执行代码」——这跟代码无关，是进程
> 启动阶段加载器就失败了。`cross-build-windows.sh` 已自动把它拷进 `dist/windows`。
> 用 MSVC 工具链构建时这个 DLL 会静态链进 exe，不需要陪它。
> 命令行版 `inputswitch-cli` 现在按 `--no-default-features` 单独构建，不带 wry，
> 产物零外部依赖，可以单文件分发。

> 为什么界面是 HTML 而不是原生控件：tao 只有窗口和事件循环，没有控件系统；
> 要做出一屏看全的界面得再拉一套 GUI 框架，而它们和 tao 的事件循环冲突
> （egui 绑的是 winit）。系统 WebView 是唯一既能跨平台、又不引入冲突事件循环的做法。

关闭窗口只是关掉，下次点菜单会重新开（约半秒）。服务只绑定 `127.0.0.1`，外网连不进来。

## 共用键鼠

两套**物理前提完全不同**的场景，装的时候要先选一种：

### 模式 A：跟随画面（软件 KVM，默认）

```
键盘鼠标 ──┐
           ├── 主机 A（键鼠插在这台）
显示器 ────┤
           └── 主机 B（不接键鼠）
```

一套键鼠插在 A 上。显示器在两台之间切，**画面切到哪台，键鼠就跟到哪台**。

- 切屏成功的那一刻，A 自动把键鼠抓过来转发给 B，B 注入回本机
- 切回 A（或按 `Ctrl+Alt+Esc`）立刻收回
- **「切换」是一个动作，不是两个**（v0.6.58）：画面和键鼠一起过去。
  画面一旦离开本机，本机连 DDC 都读不到、也写不了（实测 9/9 失败），
  面板同样看不见了 —— 所以不存在"先把画面切过去、再把键鼠送过去"这种操作，
  切回来也必须由当前握着画面的那台发起。
- 面板底部的「现在就把键鼠交给对端」在这种拓扑里会**自动隐藏**：它只交键鼠、
  不碰画面，而画面一走你就看不见这块面板了，它没有可点的时机。
- **对端不在网上时，画面一步都不动**（v0.6.63）：切屏是单行道，走了之后
  本机读不到也写不了 DDC、画面又不在本机 —— 用户既看不见光标也没法操作对端，
  只能去按显示器自己的按钮。以前这里是"降级放行"（照样切、只把失败写在提示里），
  实测结果是「切过去键鼠用不了」（那台机器整机不在网上，ping 100% 丢、
  445 连不上，键鼠根本没处可交）。现在切之前先问一句链路活不活，离线就
  **拒绝切画面**并说明原因；对端真离线时切过去也没有信号，所以这不挡正常使用。

**这种场景下没有"鼠标推到屏幕边缘"这回事**：画面已经切走了，A 的屏幕是黑的，
用户看不见光标在哪，靠撞边缘触发等于让人盲操作。所以触发点是切屏动作本身。

> 早期版本只实现了模式 B，却当成通用方案 —— 在那台没显示器的机器上永远等不到
> "鼠标撞边缘"，表现出来就是"共用键鼠完全没工作"。这是个设计错误，已修。

### 模式 B：多屏共享

```
[ 屏幕 A ][ 屏幕 B ]
  键鼠 A     键鼠 B
```

两台机器各有屏幕、各有键鼠，并排摆。光标推到 A 的右边缘就越界到 B，
在 B 推回左侧边缘又回到 A。`Ctrl+Alt+Esc` 也能交还。

这是 Synergy / lan-mouse 的经典形态。两台都要装、都开着、配对一致。

### 模式 C：多台机器，十字拓扑（v0.6.47 起）

一台机器最多可以同时挂四条链路，上下左右各一台：

```
                    (0,-1) 上
        (-1,0) 左 · (0,0) 本机 · (1,0) 右
                    (0,1)  下
```

配置在 `config.json` 的 `kvm` 段：

```json
"kvm": {
  "enabled": true,
  "mode": "edge",
  "role": "console",
  "grid_x": 0,
  "grid_y": 0,
  "links": [
    { "node": "CHINAMI-0DFF1JU", "side": "right", "mode": "edge",   "input": "" },
    { "node": "MC5K9SJ",         "side": "bottom","mode": "edge",   "input": "" }
  ]
}
```

- `side` = **本机**从哪一侧出去到它。四向天然双向：A 在 B 右边 ⇔ B 在 A 左边，
  所以**不用两边各配一次**（Deskflow 的有向边要写两遍，写漏一边就是"能出去回不来"）
- `mode` 留空 = 用外层 `mode`；`edge` 占一条边，`follow` 不占边（靠切输入源触发）
- `input` 留空 = 用对端广播的 `own_value`
- `addr` 是上次连通时记下的 IP，**别手改**（对端换 IP 后会自动回填）
- 离线分两种：**留下过 `addr` 的仍占住那条边** —— 拔网线后从它那侧推，会得到
  一句"X 没有回应，不越界"，不会先把键鼠吞掉再等 2.5 秒；`addr` 空的不占边，
  那侧推过去毫无反应（面板里连通一次就会记下）
- 同一台机器不要配两条链路；两条 `edge` 链路也不要填同一个 `side`
  （后者会让其中一条永远走不到，日志的启动行会把每条链路的方向逐条列出来对照）
- 5 台必须**全部 ≥ v0.6.47**：老版本只认一个对端 IP，会把其它三台的包静默丢掉，
  表现是"半通"
- **接收端也必须有这条链路**（v0.6.59 起会明说）：包是按「来源 IP 在不在本机的
  链路表里」判的，所以 A→B 能用的前提不只是"B 在线"，而是 **B 的表里也有 A**。
  只配一边的表现是"从这台推过去，键鼠就没了"：光标卡在边上、画面不切、日志
  安静。现在接收方会打一行
  `收到 192.168.0.40 发来的键鼠包，但它不在这台的链路表里（已丢弃）`，
  照着把那台拖进某个方向即可

#### 在面板上改链路（v0.6.51 起；v0.6.55 改成拖动摆放）

「共用键鼠」卡片里先是一张 **3×3 摆位图**，**抓着对端丢到某个方向，松手即生效**
（deskflow 那种手感）：

```
        ┌──────┬──────┬──────┐
        │斜角  │ 上方 │斜角  │
        ├──────┼──────┼──────┤
        │ 左侧 │ 本机 │ 右侧 │
        ├──────┼──────┼──────┤
        │斜角  │ 下方 │斜角  │
        └──────┴──────┴──────┘
                      ↓
        ┌──────────────────────────────┐
        │ 没有门（共用一块屏）· 拖到这里  │   未占边 / 已发现但还没配链路
        └──────────────────────────────┘
```

- **一个格子只能放一台**，所以「两台都填右侧」这种错从结构上就不可能出现 ——
  而它在逐行清单的下拉框里看着完全正常，推过去落到谁那儿却是不确定的。
  真的配重了，多出来那台会落在下面的托盘里并标「同侧冲突」。
- **四角丢不进去**：协议里一条链路只有上下左右四个门之一，越界判定是四向掩码，
  斜着没有可用的方向。拖过去会弹回并给一句提示，不会假装成功。
- **拖到下面的托盘 = 不占边**（共用一块屏，跟随画面链路）。
- **托盘里标「未配链路」的**，是发现层看到了、但配置里还没有的对端；
  拖进任意方向就等于给它建一条（后端只对**在线**的对端建，地址取自广播，不编造）。
- **键盘也能摆**：Tab 聚焦某台，方向键移动，`Delete` 放回托盘。触控板拖不准、
  远程桌面里拖不动时用这个。

下面是逐行清单（**只显示状态，不再有方向/模式的下拉** —— 那两样都由摆位图表达了，
两套控件改同一个字段只会让人不知道该信哪个）：

- 行首圆点：实心 = 对端在回包，空心 = 没回应（这时推过去只会得到一句"没有回应"）
- 中间的标签：`右侧 · 多屏共享` 这类，一眼看清这条链路现在怎么走
- **交给它**：不切屏，直接把键鼠交给这一台。一机多台时必须点名，
  程序不再猜"哪条是主链路"（猜错的表现是"点了 A，键鼠跑到 B 去了"）。
  面板底部那个**不带名字**的「现在就把键鼠交给对端」在多台在线时会直接拒绝，
  让你点名 —— 同样是"不猜"。
  这个按钮只在**空闲 + 多屏共享**时显示：共用一块屏时画面一走就看不见面板；
  键鼠已经在别台手上时（`active` 非空）抓取期间光标被钉死、点击被转发给对端，
  它物理上点不到 —— 那两种情况都藏起来，换收件人请点链路行的「转给它」。
- **「收回键鼠」按钮已删除**（v0.6.65）。它是个自相矛盾的控件：发送中光标
  被钉在钉扎点、点击转发给对端，点不到；被控时按一下鼠标就已经触发物理抢回，
  一整套按下-松开走不到 `onclick`。真正能用的两条路写在按钮原来的位置：
  **画面在对面按 `Ctrl+Alt+Esc`**（钩子里识别，抓取期间有效）、
  **被对端控制时按一下本机鼠标或任意键**即抢回。
  接口 `POST /api/kvm-takeback` 保留（脚本/CLI 用），只是不再有 UI 入口。
- 键鼠已经在别的机器手上时，这个按钮会变成 **转给它**（v0.6.60）：直接换
  收件人，**画面不动、键鼠不中断**（见下面「会话内多跳」）。空闲时才是新建
  一场会话

**方向和模式是绑定的**：拖进某个格子 = `edge`（朝那条边推出去），拖到"没有门"
= `follow`（共用一块屏，切到哪台键鼠跟到哪台）。「有门却跟随」这种半吊子组合
后端会顺手纠正 —— 它在图上画在格子里、实际却根本不占边，属于"看着正常、
推过去毫无反应"的那一类。

「发文件」入口在下面「局域网对端」卡片里按台列着，点了就发给这一台；
「文件」卡片里那个是通用入口，多台在线又没会话时后端会拒绝并报名字（不猜）。

改方向或模式会让共用键鼠实例**重启**（边缘掩码是按链路表算出来的，
热改等于掩码和实际不一致）。**重启前会先交还正在转发的会话**（v0.6.59）：
不交还就直接停，两端都以为自己在转发 —— 本机停手、对端以为还在被控制，
用户看到的是"改个方向，鼠标键盘全部失去控制"。状态条会如实说交还结果
（收回本机 / 已请对端交还 / 没能正常收场，请按热键）。
`/api/link?node=<节点名>&side=right|left|top|bottom|&mode=edge|follow` 是同一个入口，
写错的值会被直接拒绝，不会"回 ok 但其实没改"。

摆位图下面那一栏里**两种卡片标签不同**（v0.6.59）：

| 卡片标签 | 含义 | 行为 |
| --- | --- | --- |
| **没有门** | 已经配成「跟随画面」的链路 | 切信号源时键鼠跟着画面走 |
| **未配链路** | 刚发现、还没摆位的对端 | 只是一条待摆位的候选，拖进格子才建链路 |

以前两种都印「没有门」，于是"两台都在没有门里"看起来像程序认定它们共用
一块屏 —— 实际那只是"你还没告诉我它放哪儿"。对端的共用键鼠开没开也会
随广播带过来（`Message.kvm_on`，不进签名体，老端照样验签通过）：它关着的
时候 KVM 心跳一个都不会来，和对端关机/不在同一网段的现象**完全一样**，
现在链路行和「局域网对端」卡片会把这句话点破。

### 会话内多跳：键鼠在共用屏那台上，怎么再跨到并排那台（v0.6.60）

有个物理约束绕不过去：**键鼠交给共用屏那台（跟随画面链路）之后，画面就在
那台主机上，本机的面板看不见了** —— 所以"先收回、再交出去"这条路实际
不可操作。而那一台只是被注入的哑终端，它不会替你转发给第三台。

v0.6.60 的做法不是转发，是**换收件人**：本机一直抓着物理位移，只需要把
"这条流发给谁"从 A 换成 B —— `Leave` A、`Enter` B，不重启实例、不重新抓取，
**画面不动**（共用屏上还是 A 的画面，B 有它自己的屏）。

| 触发 | 说明 |
| --- | --- |
| 在共用屏上把光标顶到某个有邻居的边 | 主用方式。抓取期间平台层不判边缘（那段代码在 `!grabbing` 分支里），所以判据是拿我们转出去的那串位移在本地复刻对端光标（`EdgeSim`）：贴边 + 朝外累计 26 点 + 1.5 秒节流 |
| `Ctrl+Alt+← / → / ↑ / ↓` | 直接点方向。抓取期间系统热键收不到，所以它写在事件钩子里（和 `Ctrl+Alt+Esc` 同因） |
| 面板/托盘「转给它」 | 会话中点链路行 = 改指向；托盘另有一条「把键鼠转给下一条边（画面不动）」 |
| 从对面推回门口 | 对面交还时，如果本次会话是从别台跳过来的，**回起点**而不是回本机 —— 否则键鼠回到 Mac、画面还在起点那台上，等于看不见光标 |

几个必须知道的边界：

- **只跳一跳**。转出去之后想再转，先回起点（多跳要维护一个栈，这版没做）。
- **画面不跟着走**。所以回程落在起点那台：只有它的画面在共用屏上。
- **回程落点带位置**（v0.6.62）：`Takeback`/`Enter` 都带「出门时光标沿门轴
  的比例」，进门时按这个比例落在边缘 —— 从哪个高度出去，就从哪个高度回来，
  不再凭空闪现在屏幕正中（Deskflow 的 jump cursor 思路）。位置未知（手动改
  指向、旧版对端）时退回居中。
- 推边误判时（拖窗口到边、拉滚动条）：`kvm.push_hop` 设 `false` 就关掉它，
  只剩热键；兜底永远是 `Ctrl+Alt+Esc`（钩子里识别，抓取期间也有效）。
- 两人单链路拓扑**行为完全不变**：那条边查到的就是当前那台，改指向不触发；
  对面交也照旧收回本机。
- **会话切换不再补发鼠标键抬起**（v0.6.62）：以前改指向/交还时向旧目标盲发
  「1/2/3 键全松开」，若用户恰好按着右键，对端会收到一个孤立的松开事件，
  Windows 桌面上凭空弹一次右键菜单（实测）。按着的状态改由接收端自己清
  （它的 `pressed` 表里记着真正按下的键，收到 `Leave` 逐笔补抬起）。

#### 「从那台回不来」——门是发送方的属性（v0.6.61）

推边交还这件事**只有接收方做得到**：发送方抓取时平台层不判边缘，本地也拿不到
绝对光标位置，光看位移无法可靠区分"顶到墙上了"和"在屏幕中间往左移了 40 点"。
所以回程的可靠性取决于接收方有没有把这条链路当成**有门的**链路。

以前这个判定读的是**接收方自己那份配置**（`links[i].mode == Edge`）。而用户很自
然地只在正在用的那台上面拖摆位（"把 0DFF1JU 拖到我右侧"），接收方那份还是默认的
"共用一块屏" —— 于是它不判门，光标顶死在门口也不交还。症状就是
「MC5K9SJ 推到 0DFF1JU 正常，0DFF1JU 回不去」。

现在改成**发送方说了算**：`Enter` 里带了有效出门侧，就说明那条链路一定有门
（只有 `edge` 链路发得出 side，`follow` 恒发"未知"），接收方据此把它当有门处理，
并在日志里写一行 `… 从 right 出门 ⇒ 这条链路按「有门」处理`。进门那行日志也
会带上 `有门，门口在left` / `共用一块屏（不判门…）`，排障时一眼能看出这台
到底把它当成了什么。

**这条修复要两端都升级才生效**（判定逻辑在接收方那一侧）。在老对端上仍然有一条
与它无关的出路：`Ctrl+Alt+←`（朝来路按方向键）会直接回起点那台 —— 因为按键是
在本机的钩子里识别的，不需要对面配合。

### 切换方式

托盘 → `共用键鼠 · 开启（…）`。

面板「共用键鼠」卡片里只有开关和角色（键鼠插在哪台）、手动交还/收回 ——
**模式不在这里选**：v0.6.58 起它下沉成了每台对端自己的属性，只由摆位图决定
（拖进格子 = 多屏共享，拖进「没有门」= 共用一块屏）。以前那两个全局按钮
（「跟随画面 · 一套键鼠」/「多屏共享 · 两台各一套」）会把同一个 mode 刷给
**每一条**链路，一台机器"这台共用一块屏、那台并排"的混拓扑一点就被压平，
并排那台也跟着落进「没有门」。

托盘里那几条 `切到 <对端节点>` 只在**两台机器接同一块显示器**时成立：对端广播
的是它自己那块屏的端口编号，两块屏的 `0x0F`/`0x12` 各算各的。所以点之前会先
核一遍本机的口表，本机没有这个编号就拒绝并说明原因（v0.6.52 起）——
以前两台同款显示器时看不出来，5 台配不同显示器按下去就是黑屏。

> 切换模式会重启键盘钩子（两种模式对"没抓取时该不该盯边缘"的处理不同），
> 所以切完需要重新打开一次共用键鼠。

### 被控的时候，怎么把键鼠要回来

三条路，都不需要拔线：

| 方式 | 条件 | 适用 |
| --- | --- | --- |
| **推门** | Edge 模式，光标朝对端那条边推 | 手本来就在鼠标上，最顺手 |
| **按一下** | 按任意键 / 点一下鼠标键（1.5 秒保护窗） | 键盘用户；光标已经被对端接管时唯一的路 |
| **Ctrl+Alt+Esc** | 随时 | 兜底（被控时也生效） |
| **面板「收回键鼠」** | 被控时也行（v0.6.52 起） | 够不到鼠标、也没记住热键；脚本/接口调用 |

「按一下」的判据必须是**钩子里的物理按键**：注入来的事件带标记，在钩子入口
就被放行了，所以能走到判定点的按键一定是人按的。位移不能当判据 —— KVM 切
输入源的那一两秒，显示器会重新握手、光标坐标被重置，拿它当"用户在动鼠标"
会立刻把控制权抢回来再被按回去，来回弹。同理，进入被控后 1.5 秒内不认。

### 交还之后为什么不会立刻又被推出去

光标回来时按设计落在**边缘内侧 16 点**（左/右/上/下都是），那是"手还在鼠标上"
的位置。所以每次放开抓取都会先**撤防**这道门，光标必须真正回到屏幕内部
（离所有通向邻居的边都超过 48 点）才算重新武装 —— 在此之前怎么顶都不出去。

不撤防的后果实测过：抢回/交还之后光标停在门口，手一抖就又越界，日志里
「把控制权还回来了」和「鼠标已越界」同一毫秒出现，用户体感是"按了没用"。

### 权限

`注入`（macOS 的「辅助功能」事件投递项）是硬需求：没有它就完全没法用。
`抓取`（`AXIsProcessTrusted`）是软需求：**缺了只降级不罢工** —— 这台能收
对端的键鼠，但自己的键鼠推不出去，日志里会明说。所以键盘插在哪台都一样，
不需要改配置。

### 怎么实现的

参照两个项目的公开设计重写，代码都是自己写的（两者都是 GPL，不能照搬）：

- **[lan-mouse](https://github.com/feschber/lan-mouse)**（Rust，GPL-3.0）：
  相对位移事件、按方向注册捕捉、设备二态防回环、交还时补 key-up。
- **[Deskflow](https://github.com/deskflow/deskflow)**（C++，GPL-2.0，Synergy 血统）：
  **心跳 + 空闲超时**、**事件流加密**、**锁定到某一台**。这三条是只看 lan-mouse
  时会漏掉、但真机上一定会踩的。

为什么两个都要看：lan-mouse 离我们的语言和体量最近（好读），Deskflow 是这套
东西跑了二十多年的成熟实现（可靠）。前者给结构，后者给教训。

| 环节 | macOS | Windows |
|---|---|---|
| 抓取 | `CGEventTap`（回调返回 NULL 即吞掉） | `WH_MOUSE_LL` / `WH_KEYBOARD_LL`（返回 1 即拦下） |
| 抓住光标 | `CGAssociateMouseAndMouseCursorPosition(false)` | 钩子拦下移动事件，光标自然不动 |
| 注入 | `CGEventCreateMouseEvent` + `CGEventPost` | `SendInput` |

几个不写就出错的地方：

- **必须能吞事件**。`rdev` 这类库只能旁观，拦不住本地光标，做不了 KVM。
- **注入要打标记**。注入的事件仍会经过自己的钩子，不打标记就是死循环。
  macOS 用 `CGEventSourceUserData`（字段 42），Windows 用 `dwExtraInfo`。
- **传相对位移，不传绝对坐标**。两台机器分辨率和缩放都不同，相对位移天然跨分辨率。
- **位移要按两屏比例换算，再留一个手感旋钮**。被控端注入前先乘
  `本机宽 / 发送端宽`（对端 2560px、本机 1920pt ⇒ ×0.75），保证跨过边界后
  走过的屏幕比例不变；但**两个系统的指针加速曲线不一样**（macOS 的加速度、
  Windows 的「提高指针精确度」各算各的），同样的位移流在两边手感必然有差 ——
  实测「0DFF1JU 回到 Mac 之后鼠标比 Windows 那边慢一点」。加速度是用户级设置，
  程序猜不到，所以面板上给了「接收手感」四档（0.9 / 1.0 / 1.1 / 1.2），
  改完自动重建共用键鼠；配置文件里是 `kvm.recv_scale`（0.5~2.0）。
  进门的日志会打出 `对端屏幕 WxH，本机 WxH ⇒ 位移倍率 x…`，手感不对先看这行。
- **二态互斥**。一台机器要么在控制别人、要么在被控制，不能同时，否则 A→B→A 回环。
  多链路下这条扩展成**抢占矩阵**：正给 A 转发时收到 B 的开工请求一律拒绝
  （否则 A 还在收键鼠、B 同时开始注入，两台一起动）；已在对端控制下时收到第三方的
  开工请求，先把原来那台拆干净再换。
- **交还时补 key-up**。抓取期间按下的键，对端只收到 down，不补 up 会一直"卡住 Cmd"。
  多链路下还要注意：补发与 `Leave` 必须**显式寻址到正被释放那台**，先快照再发 ——
  清空会话目标之后补的 up 全丢。
- **事件走独立 UDP 端口**（`network.port + 3`），一个事件一个包、不确认。
  丢一个鼠标移动比用 TCP 把鼠标粘住强。
- **必须有心跳**。UDP 是无连接的，对端进程崩了、Wi-Fi 断了，本机收不到任何东西，
  但仍停在"正在控制对端"，于是把自己的键鼠全吞了 —— 用户看到的是鼠标没了、键盘也死了。
  Deskflow 用空闲超时解决，这里照做：每 800ms 发一次 `Ping`，2.5 秒收不到任何包
  就强制交还并写日志。
- **事件流要加密**。Deskflow 默认 TLS。我们配对后用配对码派生的密钥做
  ChaCha20-Poly1305（每个包 25 字节开销，不用握手、不用证书）。没配对时是明文，
  日志和面板都会警告。
- **锁定到本机**。拖窗口、拖分隔条的时候鼠标很容易撞到边缘，一撞就切走很烦。
  菜单 → `锁定在本机` 打开后，撞边缘也不再切出。

### 权限（macOS 必须做，只做一次）

系统设置 → 隐私与安全性：

- **辅助功能**：勾上 InputSwitch —— 抓取和注入都要它
- **输入监控**：勾上 InputSwitch —— 抓键盘要它

⚠️ 我们是 ad-hoc 签名，**每次重新编译 cdhash 都会变，授权会失效**，
表现为"看着在跑但鼠标抓不住"。需要去列表里删掉旧条目重新添加。
根治得用 Developer ID 证书做稳定签名（99 美元/年）。

⚠️ **勾完必须重启本程序**（顺序：先勾、再启动）。macOS 把 TCC 的结论缓存在
进程里，已经跑起来的进程即使你刚勾上也照样报「没权限」——这时点
「开启共用键鼠」只会再弹一次设置页，看起来就像勾选无效或者装错了版本。
已经在跑时点托盘菜单里的 `⚠ 系统授权没生效 · 点这里重启应用`
（或面板「共用键鼠」卡片里的「重启应用」按钮）即可。

> 这也解释了为什么 `inputswitch-cli kvm-probe` 天天报 ✗：它是包里的第二个
> 二进制、另一个 cdhash，TCC 只认主程序。判权限看 `/api/state` 的
> `perms.capture` / `perms.inject`。

Windows 不需要授权。但安全软件可能拦 `SetWindowsHookEx`，被拦时菜单会报错而不是静默失败。

### 自检

```bash
inputswitch-cli kvm-probe                       # 看权限和屏幕尺寸
inputswitch-cli kvm --peer 192.168.0.40         # 直接跑，不经过托盘
inputswitch-cli kvm --peer 192.168.0.40 --side left --seconds 30
```

> **`kvm-probe` 报的权限不可信**：它是包里的第二个二进制，有自己的 cdhash，
> TCC 只认主程序 → 它永远报「没权限」，而 GUI 实际是通的。
> 判权限一律看 `curl /api/state` 里的 `perms.capture` / `perms.inject`
> （v0.6.52 起由 GUI 进程自己上报）。

## 传文件

面板「文件」卡片里点 `发送文件…`，或者点对端卡片上的 `发文件`。

- 走 TCP 47832，复用发现层已经知道的对端 IP，不用再填地址
- **发给哪台**：有会话就发给"现在握着键鼠"的那台；只有一台在线时就是它；
  多台在线又没有会话时**直接拒绝并报名字**，不会替你猜（v0.6.52 之前固定发
  排序第一的那台，多机时必然发错人，而且界面上看不出来）
- 支持多文件和整个目录（保留相对路径）
- 每个文件 SHA-256 校验，对不上直接丢，不会留一个看起来正常的坏文件
- 重名不覆盖，自动加 `(1)`
- 接收目录默认 `~/Downloads/InputSwitch`，可以在面板里改
- 对端塞 `../../` 这种路径会被拒绝

```bash
inputswitch-cli send ~/Desktop/报告.pdf     # 命令行直接发（不用开托盘）
```

## 剪贴板

面板「设置」里点 `同步剪贴板文本` 那一行的开关。

500ms 轮询一次变更计数，内容哈希去重防回环。只同步**文本** ——
图片和文件列表要各自处理格式转换，暂时没做。

**同步给谁**：和发文件同一套规则 —— 有会话只发握着键鼠的那台，没有会话才广播。
以前是无条件广播，四台机器时复制一句话会同时改掉四台的剪贴板。

```bash
inputswitch-cli clip             # 读当前剪贴板
inputswitch-cli clip "测试文本"   # 写进去（自检用）
```

## 一个必须知道的副作用

**Windows 会认为显示器被拔掉了。** 切换走后桌面图标可能重排、窗口会挤到主屏。
这是纯软件方案的天花板 —— Windows 的显示拓扑跟着物理连接走，DDC 切换等同于拔线。

要彻底解决只有一条路：带 EDID 模拟的硬件 KVM，它能让非活跃端口保持"假在线"。
但那就不是软件能做的事了。

## 从源码构建

```bash
cargo build --release --bins
```

产物两个二进制，必须分开编，原因在 Windows 上（名字不能只差大小写 ——
macOS 文件系统不区分大小写，`InputSwitch` 和 `inputswitch` 会互相覆盖）：

| 二进制 | 子系统 | 用途 |
|---|---|---|
| `InputSwitch` | windows（GUI） | 托盘本体，双击不弹黑框 |
| `inputswitch-cli` | console | 命令行诊断，终端里能看到输出 |

打包脚本：

```bash
./build.sh          # macOS → dist/InputSwitch.app（含图标、ad-hoc 签名、LSUIElement）
.\build.ps1         # Windows → dist\windows\InputSwitch.exe
```

在 macOS 上交叉编 Windows 版需要 `rustup target add x86_64-pc-windows-gnu` 加 mingw-w64 工具链；
最省事的是直接用 Zig 的 `zig cc` 当链接器。

## 三个平台的 DDC 实现

| | Windows | macOS | Linux |
|---|---|---|---|
| 通道 | `dxva2.dll` | IOKit `IOAVService*I2C` | `ddcutil` 子进程 |
| 读 VCP | 稳定 | **多数机器读不到** | 稳定 |
| 写 VCP | 稳定 | 看连接方式 | 稳定 |
| 句柄 | `GetPhysicalMonitorsFromHMONITOR` 拿的物理句柄 | `IOAVServiceCreateWithService` | `/dev/i2c-*` |

Windows 上一个高频坑：`SetVCPFeature` 的第一个参数必须是
`GetPhysicalMonitorsFromHMONITOR` 返回的**物理监视器句柄**，直接传 `HMONITOR` 一定失败。

macOS 上 DDC 走 Display Coprocessor，读操作经常返回未初始化内存。代码对每一帧做
校验和 + 长度位校验，不通过一律返回 `None`，**绝不把垃圾当数据**。这是有实测依据的：
某台 P275MV PLUS 在 USB-C 下连续 24 种请求帧组合，返回的都是同一串 `6e 80 be ...` 垃圾。

## 代码结构

```
src/
├── models.rs     数据结构、VCP 常量、MCCS 标准值表
├── config.rs     配置持久化（profile 按显示器型号索引）
├── switcher.rs   切换编排、拓扑验证、输入源发现
├── peer.rs       UDP 广播发现 + 中继指令
├── autostart.rs  开机自启（LaunchAgent / 注册表 Run）
├── tray.rs       托盘 + 全局热键（tao 事件循环 + 工作线程跑 DDC）
├── gui.rs        托盘入口（windows 子系统）
├── main.rs       CLI 入口（console 子系统）
└── ddc/
    ├── mod.rs    后端 trait
    ├── mac.rs    IOKit IOAVService（纯 FFI，无第三方绑定）
    ├── win.rs    dxva2（纯 FFI）
    └── linux.rs  ddcutil
```

加新平台只需实现 `ddc::Backend` 的 `list_displays` / `get_vcp` / `set_vcp` 三个方法。
